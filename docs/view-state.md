# Reproducible view state

View-state files record display settings for an explicitly identified anatomical asset. They contain no experimental measurements, imported dataset metadata or user research-file paths. Saving or restoring a view does not publish data, contact a service or persist anything in browser storage.

The canonical JSON document uses schema version `mousebio.view.v1` and binds the view to three values from the loaded atlas manifest: `atlasId`, the GLB `assetSha256`, and `coordinateFrameId`. All three must match exactly before any settings are accepted. A source atlas name alone is insufficient because a changed mesh or frame could invalidate structure associations and camera coordinates. This binding compares declared manifest values; it is not an independent cryptographic verification of the asset currently rendered in memory.

The format accepts earlier `mousebio.view.v1` files that omit only the viewer background field: an absent `background` is restored as `dark`, matching the earlier viewer setting. This narrow migration does not infer or replace atlas identity, asset checksums, coordinate frames or other required controls. Earlier experimental exports without those bindings or complete living controls are not supported. Unknown schema versions and explicitly invalid background values are rejected. Export always writes the canonical background value. Future migrations must be explicit and must preserve the meaning of anatomy and coordinates.

## Stored settings

The settings record contains the exploration `mode`, nullable selected structure ID, hidden structure IDs, opacity mapping, display clipping axis and position, selected-label visibility, viewer `background`, and living display controls. Background is either `dark` or `white`; it changes display presentation without altering anatomy, scientific classifications or observations. Living controls comprise `playing`, `speed`, `cardiac` and `respiratory`. A camera pose is optional so that a view saved before the renderer becomes ready can still preserve the interface settings.

The camera pose records world-frame `position`, `target` and `up`, each as three numbers. The up vector preserves camera roll. These are viewer display coordinates after centering and presentation rotation, not anatomical orientation labels or a new source registration. Serialization and `scene-utils.validateCameraPose` share the pure validator in `camera-pose.ts`. It requires finite vectors, nonzero finite squared lengths and normalization reciprocals for the viewing and up directions, and nonparallel normalized directions. The squared normalized cross-product threshold is `1e-24`. It also checks that the renderer can normalize the side vector obtained by crossing the original up vector with the normalized viewing direction. Vector components and the resulting view translation must remain finite when represented as Float32 values for GPU matrices. These arithmetic guards reject extreme vectors whose mathematical lengths are nonzero but whose squared lengths overflow or underflow, and large translated views that exceed the renderer's representation. They are numerical display constraints, not claims of calibrated anatomical dimensions. No Three.js dependency is imported into the view-state module, preserving the separation between data validation and the lazily loaded renderer.

Opacity values are finite numbers from zero to one. Selected, hidden and opacity identifiers must exist in the loaded atlas. Hidden IDs are unique; a selected structure may also be hidden so that inspector state can be restored. The module accepts maps that omit structures, in which case the application supplies its current defaults. The current interface saves the effective opacity of every structure to retain the visible state independently of those omissions. Clipping permits `off`, `x`, `y` or `z` and a finite position from zero to 100 percent. These are display axes and do not establish anatomical directions. Living speed is a finite display multiplier from 0.25 to four; it is not a physiological rate.

The file does not include an animation phase, accumulated physiological time, experimental data, colour-overlay values, measurement selections, experimental condition selections or imported observations. Opening experimental or comparative mode through a saved view does not recreate the data previously used in that mode. A view-state file therefore reproduces the recorded settings and anatomy association, rather than an entire research session. The physiological animations remain illustrative.

## Validation and serialization

`exportViewState(state, atlas)` validates the settings and manifest binding before returning readable JSON, always including `background`. `parseViewState(text, atlas)` returns `{ ok, state?, errors }`; any error returns no partial state. Files are limited to 1 MiB measured as UTF-8 bytes. Malformed JSON, nonobject roots, missing required fields, unknown fields, prototype-related keys, unmatched bindings, unknown or duplicate IDs, unsafe numbers, incomplete living settings, invalid backgrounds and invalid camera poses are rejected. The only default applied during import is `dark` for an absent background in an otherwise valid bound v1 file. Fields are not coerced from strings or numeric booleans. A byte order mark is accepted at the start of a file.

The serializer emits fixed top-level field order, sorts hidden IDs and opacity keys, and copies all accepted arrays and objects. This gives deterministic JSON for the same validated settings without mutating caller state. It does not invent absent geometry or resolve unverified physical calibration. Numbers use ordinary JavaScript floating-point representation, and this format is not an arbitrary-precision numerical interchange standard.

The pure module performs no network requests, file-system writes or browser persistence. The current application reads a file locally, applies an accepted state atomically and initiates a download when requested. It discloses a rejected file while retaining the current view. Restoring a saved view does not clear, replace or transmit research observations. The latest file attempt takes precedence if asynchronous reads finish out of order.

## Acceptance criteria

The view-state tests exercise a complete round trip with camera roll, all four modes, dark and white backgrounds, the narrow legacy-background migration, continuous supported display speeds, a missing camera pose, null selection, exact source binding, malformed and oversized files, UTF-8 byte accounting, strict nested schemas, prototype keys, known-ID constraints, visibility and opacity settings, clipping, living controls, camera degeneracy, nonfinite values, deterministic ordering, nonmutation and exclusion of research-data fields. A legacy file with a mismatched or missing source binding must still fail. These checks establish serialization and validation behavior. Browser restoration, renderer readiness, camera application and actual downloaded-file contents require separate interface acceptance checks.

On 2026-10-26, the focused WSL run passed all 15 view-state cases and two translated-camera regressions, with no failures or skips. The TypeScript integration check passed. This includes dark and white background round trips, canonical exports, legacy files defaulting to dark only when all source bindings remain valid, atomic rejection of invalid explicit backgrounds and exclusion of experimental observations. These results establish serialization, validation and compile-time integration. Actual browser restoration, GPU performance and visual rendering require separate checks.

## Reference selection and regional surfaces

Each view file binds to one anatomical reference through its atlas identifier, asset checksum and coordinate-frame identifier. Select the matching reference before loading its view file. A file from the other reference is incompatible; source-label numbers and numerical coordinates must not be used to translate it.

Optional finer regional surface selection is transient and is not serialized in a view file. Successfully loading a view restores the selected reference's base geometry. Experimental observations remain separate from view files and stay associated with their original reference in browser memory.

Source-group labels are also transient display controls. Their resulting selected source ID, hidden regions, opacity, clipping and optional camera pose are saved through the normal fields. Loading a valid view restores those settings and shows Current view in the group selector. It does not infer a source group or change the observations.
